# Gameplay, workflow and repository assessment

## Decision

Authentic useful gameplay is the primary behavioral feedback loop. The repository
already stated development-first delivery, but operating practice accumulated
extra full-PR/actual-main gates before development attempts. Those gates delayed
real feedback without qualifying the assumptions that mattered. Use inspected,
committed fast/focused checkpoints for finite development play; consolidate broad
regression, independent outcome review and protected publication at integration
and formal acceptance. Applicable authority, identity, uncertainty, native/version,
cleanup and resource faults still block affected play.

The user explicitly prioritizes revealing organic gameplay over API cost savings.
Use coherent useful objectives, sufficient finite continuation and observed game
consequences. Learning/revision/reuse must arise from actual experience. Preserve
an unmet acceptance criterion instead of manufacturing a task or correction to
make the demonstration pass. Choose a configuration for useful outcomes and
apparent time to useful progress, including local program execution. Call counts,
request duration, cache hits and token prices remain diagnostics.

Current guidance lives in the [development workflow](../project-management.md#gameplay-as-the-primary-feedback-loop),
[S-WORK/S-OPS](../engineering.md) and [overview](../overview.md).
[Audit issue274](https://github.com/CVX-Hull/enactive/issues/274) owns this finite
assessment and publication; closed [assessment75](https://github.com/CVX-Hull/enactive/issues/75)
retains its original scope. [Iteration264](https://github.com/CVX-Hull/enactive/issues/264)
remains incomplete. No new game or provider request was allocated during this audit.

## Documentation and repository shape

Retain the current responsibility hierarchy: overview/charter/standards, system
architecture, five component views, exact protocol/schema/source, operating guides,
then dated evidence/rationale and authoritative GitHub work. Shared code belongs in
`harness/`, CDDA integration in `native/`, maintained tools in `tools/`, passive
presentation in `web/`, and assertions in `tests/`. Existing coupling remains named.
Ignored run directories retain frozen data/evidence; they are not a second source
tree or live work tracker. No new documentation service, registry or metrics store.

The changes repair navigation without relocating evidence: a direct player path
in the [documentation map](../documentation.md), an explicit directory ownership
table, a task-oriented [protocol index](../protocol.md#contract-navigation), and
six stable evidence families in [work](../work.md) instead of eighteen dense rows
of attempt summaries. Original dated reports, source IDs and screenshots remain
unchanged; the native017/018 record is consolidated into its existing evidence
family. Current pages explain behavior and limits rather than accumulating another
per-run checkpoint. These changes do not claim measured usability improvement.

The directory hierarchy is reasonable; the content does not yet support focused
reading/review well enough. The protocol and policy files remain large references
mixing several reader needs. Issue #276 owns decomposition into task-sized current
contracts and separate explanation/procedure/history, using the existing component
boundaries. Reader acceptance covers Load/adoption, recovery, handoff, collection
and development-versus-acceptance lookup without reading the full corpus. No
formal usability study or arbitrary byte quota is claimed.

The four affected control entries had accumulated chronological evidence
inventories. Their definitions now use current mechanism/assertion links and
representative evidence families; original reports remain in Git. This reduces
the generated map from 90,864 to 72,976 bytes. C-REVIEW/C-USABILITY/C-MAINTENANCE
mechanisms are clearer, with honest partial-effectiveness records and unchanged
January 15, 2027 due dates. C-RUNTIME records the latest native018 failure on
its original source; new source/contract review is not a repaired native exercise.

MissionRuntime/ledger also remain large source owners. Split by a demonstrated
interface/reader responsibility when doing so reduces change/navigation cost.
Current module boundaries and links must migrate together; Git retains the prior
layout. The present audit establishes no need for a new generic adapter framework.

## Verification and retained limits

The handoff change is exercised through actual pinned Pi serialization and owned
Python MCP subprocesses against synthetic providers. Cases cover mixed batches,
direct completion, this-host pending/uncertain collection, successor issuance
reads, both transport uncertainty and presentation exceptions, proven nonadmission,
missing immediate snapshots, actual HTTP/MCP assigned-identity preservation,
plain-text collection errors, newer read-only samples, refusal/pending and
incoherent receipts, cancellation/cleanup dominance and CLI zero exit with empty
final text. Initial CLI execution hit sandbox loopback EPERM; the allowed offline
host execution passed. This was an environment failure, not a green result or a
gameplay failure. No API credential or actual model/game was used in these tests.

Fast structural/document checks, focused host/driver behavior, independent final
review, applicable protected full PR and actual-main validation and tracker
readback are required for this audit's source delivery. Exact candidate/check and
publication receipts belong to issue274/its PR; they are not duplicated as another
source-history inventory here. An audit/CI pass cannot qualify organic usefulness,
corrected-program successor application, apparent cadence or independent survival.
Those remain in264/164/145 and their existing parents. No closed actor or retired
attempt allocation is revived. Further gameplay starts only after this audit's
closure and a newly selected finite development scope.
