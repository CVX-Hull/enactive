# Curator sessions, drafts and gate v0

This is the curator's workspace, persistence and publication path from
[ADR 009](../decisions/009-curated-player.md#the-curator-as-a-coding-agent-d14), version 0.
It is enough to run scripted and shadow sessions over sealed traces. Not yet: live actor
integration, gate-owned prospective tests and computed utility (#459), and executing
submitted programs. **v0 runs nothing a submission contains**; it validates and publishes
data.

Code: [`harness/curator`](../../harness/curator): `knowledge.py`, `containers.py`,
`session.py`, `gate.py`, `window.py`.

## Layout

The repository layout is `curator-knowledge/2`, recorded in `knowledge.json`. Readers and
writers refuse other repository schemas with “start a new repository”; there is no
layout migration. The knowledge repository's location is set by ADR 009's
[owner decision on where the repository lives](../decisions/009-curated-player.md#open-owner-decisions).
Everything lives under one project-local root, by default
`.runtime/knowledge/`:

| Path | Holds |
| --- | --- |
| `<game>/` | The knowledge repository: a Git repository with `ontology/`, `programs/`, `tests/`, `facts.jsonl` (facts and articles), `knowledge.json`, `provenance.json` and, from the first publish, `coverage.json`. Only the gate commits. Each publish is one commit on `main`, tagged `v<N>`. |
| `<game>.state/sessions/<id>/` | One curator session's record: `manifest.json` (`container-manifest/1`, kind `curator-session`), `brief.md`, the host's output, and the submissions and gate results. Kept after close. |
| `<game>.state/drafts/<id>/` | One draft: `manifest.json` (kind `draft`) and its files. Persists across sessions until promoted or expired. |
| `<game>.state/workspaces/<id>/` | The ephemeral workspace, deleted at close. |
| `<game>.state/gate.jsonl` | Gate verdicts, in order. |

## Workspace

A session's workspace follows ADR 009's table:
- `trace/`: the trace window, as a [`harness.trace` projection](trace-workbench.md).
- `knowledge/`: an export of the published version. It contains no `.git`, so a session
  sees no history it could rewrite.
- `brief.md`: generated by software.
- `workbench/`: a copy of `harness/trace`, run with `python -m harness.trace.workbench`.
- `submissions/`, `drafts/` and `scratch/`: the only writable places.

Open and stale drafts are copied into `drafts/<id>/` so the session can continue them. The
host runs under the [curator sandbox](../research-curator-sandbox.md).

## Submissions

A submission is a directory `submissions/<id>/` with `submission.json`:

```json
{"schema": "curator-submission/1", "base_version": "v3", "summary": "…",
 "changes": [{"op": "add_fact", "fact": {"schema": "curator-fact/3", "record": "fact", "id": "f12",
              "type": "relation", "text": "…", "scope": {"game": "example"}, "citations": ["frame-id"]}}]}
```

The [general-memory design](general-memory.md#the-format-curator-fact3) owns the field
meanings. These are the gate's exact submission shapes:

| Record | Fields |
| --- | --- |
| Fact | `schema: curator-fact/3`, `record: fact`, `id`, `type`, `text`, `scope` (at least a non-empty `game`), non-empty distinct `citations`, optional non-empty `subject` |
| Article | `schema: curator-fact/3`, `record: article`, `id`, `title`, `lead`, `body` (a non-empty list of `{text, facts: [ids]}` claims, each with at least one distinct fact id), `links` (distinct article titles; may be empty) |
| Type | `schema: curator-type/1`, non-empty `name`, text `description`, `fields` (a list of strings) |

Software adds `published_in` and `session` to each record. It writes a fact's `seen`
from the latest cited frame's trace position, and an article's `last_confirmed` from
the latest `seen` of its cited facts. Positions carry `session`, `actor`, `step` and
`order` (an ordered triple of admission ordinal, actor directory and step); order
compares sightings, not elapsed time. Replaying earlier windows preserves trace order. Neither timestamp is accepted
from a submission. Leads are one or two sentences by curator instruction; the gate
does not parse or judge their prose.

| Operation | Exact fields beyond `op` |
| --- | --- |
| `add_fact` | `fact` |
| `supersede_fact` | `ids` (one or more distinct current fact ids), replacement `fact` |
| `retire_fact` | current `id`, non-empty `reason`, non-empty distinct `citations` in the session window |
| `add_type` | `type` |
| `add_article` | `article` |
| `revise_article` | current `id`, replacement `article` with a new id |
| `retire_article` | current `id`, non-empty `reason` |
| `revise_types` | `action`, `names`, `types`, `assignments` (fact id to new type name) |

`revise_types` is grooming-only. A merge takes at least two existing names and one
new type; a split takes one name and at least two new types; a rename takes one name
and one new type; deprecation takes one name and no new types. Every current fact must
end with a current type. Each revision publishes a new version, so at most one type
revision is allowed per submission. An assignment's fact must be current, have a type
in `names` before the revision, and survive the submission (neither retired nor
superseded). Software appends `{from, to, version}` to that fact's `retyped` list;
submissions cannot supply it. Git retains the prior ontology and fact history at each
version.

Superseding or revising marks every target with `superseded_by`; retiring marks it
with `retired` (reason, citations for facts, publication and session). Historical
records remain evidence. Only records without either marker are current. Record ids
are new across both kinds, including history; each target can change once per
submission. Articles cannot link to themselves. Current article titles are unique
(one article per curator-chosen subject).
Split or merge articles by replacing/retiring predecessors and adding the resulting
articles, repairing incoming links and fact references in the same submission.

One current contract, no shim: the gate and session runner refuse stores containing
records outside `curator-fact/3`. The read-only `store` and `replay` commands also accept
only this record contract and the `/2` repository layout. They read fact `text` and
separate facts from articles. `store` reports total and current counts for each kind
and the bytes of `facts.jsonl` per version, so grooming size is measurable. Sealed old
stores remain evidence and are neither
migrated nor opened as input to curation. The finished `brief-gate` check is retired
(R-TECH-DEBT).

## Admission and grooming

`run_session(..., session_kind="admission")` reads the supplied trace window and the
whole published store. It may leave new facts unfiled. `session_kind="grooming"` runs
between admissions with the whole published store and only the last admission's cited
frames and their steps. It receives its own `grooming.md` brief alongside the shared
instructions. The host passes its path through `SessionConfig.grooming_brief`; the
runner copies it to the workspace and retains its contents and SHA-256 in the session
record. A grooming session without that configured path aborts before the host starts.
It cannot take a restricted window; the supplied sealed trace sessions
must match the last published admission's names, and every retained citation must exist.

`provenance.json` keeps software-derived frame positions and the last admission's
coverage and citations. Citations accumulate across accepted windows of the same
admission. A grooming publication retains that admission stamp. Grooming replacement
facts may cite the union of the superseded facts' citations and the current window's
frames; other fact operations and retirements require window citations. Software
looks up inherited frame positions in recorded provenance and writes `seen` from the
latest cited position. Citations of unrelated facts do not qualify, even if recorded
provenance contains them. The curator merges
and retires facts, normalizes subjects through replacements, revises types, and writes
articles, leads and links. Every grooming publication must file every current fact in
at least one current article. There is no hard cap on the store; submission and host
resource limits still apply. The first paid grooming run measures store size and is
priced and asked of the owner separately. The stand-in provider covers admission then
grooming end to end at zero spend.

## Windows of decisions and the coverage stamp

A session reads either whole admissions or a **window**: one actor of one sealed
session and a range of its steps (`seq` in `steps.jsonl`, first and last inclusive).
A window counts steps, which are the actor's computer operations; it does not count
provider requests, and an actor may make requests that produce no step. The session and
actor names are `[A-Za-z0-9_-]+`; the steps are integers.
Both take one path, [`harness/curator/window.py`](../../harness/curator/window.py): the
projection is written whole and `restrict` narrows it in place; with the full window
(`Window()`) it changes nothing.

- **What a window keeps.** The actor's steps in the range, the tool calls that belong to
  them, the frames those steps returned, the actor's received prompt and guide. A tool
  call belongs to the step its result names (`operation_id`); a call that names none (a
  memory or handoff tool, an unanswered call) belongs to the step of the next call that
  does, and a call after the last such call belongs to the last step.
- **What it drops**, because each reports beyond the range: the other actors, handoff
  packets, the sealed memory store and the actor's final report. A runner that passes a
  memory store with a window still gets none of it.
- **The manifest says so.** `trace/manifest.json` gains `window` (session, actor, first,
  last as clamped to the steps that exist, `steps_available`) and lists
  what was dropped; its file hashes are of the narrowed trace. The brief names the
  window. A window that starts after the actor's last step aborts the session before the
  host runs.
- **Provenance follows.** Frames outside the range are not in `trace/frames/`, so the
  gate refuses a citation of one.
- **Coverage stamp.** The runner derives `curator-coverage/2` from the window: `session`,
  `actor` and `last_step` (the last step read). The session passes the stamp to the gate with every submission it gates, and the gate writes it
  as `coverage.json` beside `facts.jsonl`, so each tagged version records what it covers.
  A whole-admission session stamps its session names with no actor or last step. The
  curator never writes it: a submission carrying `coverage` is rejected as an unexpected
  field, and the gate refuses a stamp that is not exactly those keys.

## Gate v0

The gate applies its checks in this order, and the first failure rejects:
1. The submission is well formed: a known schema, known operations, no extra fields, and
   at most 200 changes and 256 KiB.
2. **Base version.** `base_version` is the published version. Otherwise the submission
   is stale and is rejected, with the current version in the diagnostics.
3. **Candidate snapshot.** Apply operations atomically to a candidate. Types and targets
   exist, ids are new, scope matches, and citations belong to the window or, for a
   grooming replacement, to the facts it supersedes. Software derives sighting positions
   from the trace projection and recorded provenance.
4. **References and filing.** Every article claim cites current facts and every link
   names a current article in the final candidate. Titles are unique. Grooming files
   every current fact; admission may leave facts unfiled. This checks structure only,
   never what an article says. These tests address R-GAME-COUPLING and R-REGRESSION;
   they require no semantic model calls.

An accepted submission is published atomically: one commit, one new tag, then the
`published` pointer moves. A rejected one returns its diagnostics in the next session's
brief. Only the gate writes the repository, so no lead text enters published knowledge.

## Drafts

A draft is a container (`container-manifest/1`, kind `draft`).
- **Lifecycle.** `open` until it goes 3 sessions untouched, then `stale`. After 3 more
  untouched sessions it becomes `abandoned` and is archived.
- **Renewal.** A session that writes to a draft renews it.
- **Promotion.** A draft is promoted when a submission that names it in `from_drafts` is
  accepted.
- **Expiry is a policy, not something the curator must remember.**
- **Aborted sessions** keep their drafts, and do not age the others.

## Session close-out

**On close.** When a sandbox result is available and reports no survivors, the runner
collects `submissions/` and `drafts/` back to the session's state directory. It gates
submissions only after a clean exit, updates draft lifecycles, seals the session record
and deletes the workspace. Without a result it collects nothing; exit/provenance and
survivors remain unknown (`null`), rather than an invented successful cleanup observation.

**Collection never follows a link.** The sandbox lets the host replace a writable
directory itself, for example removing `drafts/` and putting a symbolic link in its place.
So every collected tree is examined without following links, the writable directories
included.
- A writable directory that is no longer a plain directory is not collected.
- A draft that is, or holds, a link or a special file is refused.
- Any link or special file under `submissions/` stops all gating for the session.

Each refusal is listed in the record.

**Close-out reads through directory descriptors.** A host process that escaped the stop
with `setsid` is not listed as a survivor and may still be writing. So every collected
tree is walked component by component.
- Each component is opened relative to its parent's descriptor with `O_NOFOLLOW` and
  checked with `fstat`, so a link swapped in during the walk refuses the tree rather than
  redirecting it.
- Sizes are checked from `fstat` before reading. A tree over its limits is refused, never
  truncated.
- The limits:
  - a draft: 4 MiB;
  - all submissions together: 16 MiB;
  - entries per tree: 10,000.

**On abort.** A crash, a breached limit or a handled failure records the session as `aborted`
where the record is writable. A failure before gating prevents submissions from being gated;
a later failure cannot undo an earlier atomic publication, whose verdict remains retained.
After an observed unclean exit, collectable drafts are kept without aging the others.
If host processes survive the stop or no sandbox result is available, nothing is collected.
Removing the workspace clears file flags and permissions first. A removal failure is
recorded in `cleanup-failed.json`, and the lock is always released.

**Interruption during preparation or execution.** `KeyboardInterrupt` attempts an aborted
close-out before re-raising the original interrupt; it gates nothing without a clean result.
The sandbox's process-tree cleanup and the outer workspace/lock cleanup still run. If the
process-tree or profile cleanup fails, the original interrupt propagates with safe failure
notes retained in the session's errors; unknown cleanup cannot admit another shadow session.
Both cleanup steps are attempted even when one fails. If the
interrupted close-out itself fails, `close-out-failed.json` retains the safe error category
where writable, and the original interrupt remains primary. A forced second interruption,
hard kill or unwritable record can prevent a terminal receipt; that remains unknown.
This guarantee does not cover interruption during later collection/gating and cannot undo
an earlier atomic publication. Proxy shutdown and unsettled accounting are separate
[runner guards](../operations/curator-hosts.md#pi-curator-host-the-shadow-session-host).

**One session at a time per repository.** The runner holds an exclusive lock on
`<game>.state/lock`.
