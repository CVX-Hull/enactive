# Player architecture, delivery ergonomics and runtime control: `player-host/12` and `player-knowledge/3`

## At a glance

- **Question.** What bounded `S-MIGRATION` (`player-host/11` → `player-host/12`, telemetry `11` → `12`, conditional `player-knowledge/2` → `player-knowledge/3` if compact query hits are selected, conditional `player-computer-result/2` → `player-computer-result/3` if post-batch settle or pixel-change flags are selected, and conditional `player-source-read/1` → `player-source-read/2` if lossless crop is selected) resolves the real bottlenecks still present on `main` (`b4fb998b`) — actor-start briefings growing to `51,601` chars in the seven-day campaign (`#896`), `71.1%` pre-cut duplicate reminder leads (with all `47` `v91` articles still fitting in `cutBriefing` from KV-cache hardening `#920`), `12,987`-token recall prompts (`$3.99` / `10.8%` of play+recall), `cutContext` premature-break and level-triggered holdbacks, spend/finish-reserve races, `10,946 B` full-record query bloat after Wave 3 knowledge migration (`#937`), broken `_fold` stemming, and `89.7%` terminal `wait` actions — while preserving [ADR 006 (computer-control boundary)](../decisions/006-computer-control-boundary.md), [ADR 008 (evaluation and spectator)](../decisions/008-evaluation-and-spectator.md), [ADR 009 (curated player)](../decisions/009-curated-player.md), `P-GENERALITY`, and programs-and-monitor (`#177`) actor-port parity?
- **Companion evidence & bug split.** This player architecture RFC ([#947](https://github.com/CVX-Hull/enactive/issues/947)) pairs with [player architecture research](../research-player-architecture.md) (player research [#945](https://github.com/CVX-Hull/enactive/issues/945)), where all empirical figures and version-boundary caveats (`0ff6ace5` vs. `main` `b4fb998b`) live. Fourteen grouped contract-preserving `player-host/11` bugs and dead-code removals (`validation-feedback.mjs`, `7` unproduced `player_view.py` strings) are separated into player runtime bug fixes [#946](https://github.com/CVX-Hull/enactive/issues/946) (zero schema bump).
- **Summary of proposed changes.**
  1. **Bounded actor-start briefing:** `24,000`-character serialized envelope inheriting `cutBriefing`'s `64`-article / `24`-fact caps and skip-if-oversized rule, in fixed tier order (recall leads → articles by `last_confirmed` → non-`instance_state` standalone facts by `seen` → `instance_state` standalone facts by `seen`; no ordinary update-lead clip).
  2. **Context-aware recall dedup & bounded title-first recall index:** pass `already_in_context` IDs inside recall user message 2's JSON after `recent_calls` (preserving message 1's cached index prefix), filter identical normalized unclipped leads at placement, budget message 1 within `24,000` characters title-first in §2.1 tiers 2–4 (reserving tier 1 for the subsequent briefing), and tighten logical `knowledge-delivery` attribution across all terminal paths.
  3. **Closed-form `context_cut` hysteresis, strict-fit hard-capacity rescue, atomic update+cut & halving notices:** arm-on-pressure holds, smallest-sufficient `k in [min_free, E]` satisfying targets and `fits(R_k)` (holding with `insufficient-cover` when none qualifies), independent strict-fit hard-capacity rescue over the original uncommitted projection `k in [1, E]` under all three cut guards, atomic newest-first update+cut commit preserving the existing `context_reserve_tokens` update-admission threshold, halving-step `tail-notice` placement (`100%/50%/25%/12.5%`), and optional last-5 distinct `recent_intents` in `BEGIN CONTEXT CUT`.
  4. **Terminating spend-limit & `finish_reserve` handshake:** preflight `ending_reserve.usd + reserve_bound < spend_limit_usd`, one-shot `spend-reserve-reached` event consumed by the live driver (preserving Pause/deadline/EOF/spend-limit reasons without masking), and releasing `finish_reserve` **only** for a request whose projected context carries the accepted `control_id`.
  5. **`player-knowledge/3` compact query hits, casefolded title lookup, Porter2 stemmer & parity vectors:** discriminated compact hit shapes (`-64.0%` total / `-62.0%` median `Knowledge._result` `canonical` UTF-8 bytes across the `20` open-horizon knowledge research [#924](https://github.com/CVX-Hull/enactive/issues/924) `v91` queries replayed in retrieval baseline [#936](https://github.com/CVX-Hull/enactive/issues/936)) preserving `judge.ROUTES` (`lead`/`read`/`index`/`withheld`), exact-title-first casefolded lookup, pinned `snowballstemmer` (`requirements.in` + `requirements-dev.lock`, gated on the `#924`/`#936` regression check), and zero new Node dependencies (knowledge-graph scoping RFC [#925](https://github.com/CVX-Hull/enactive/issues/925) rule kept) with hardened parity vectors.
  6. **Optional observation, provider & `cites` choices (individually voted in §9):** opt-in post-batch visual `settle` (`changed_during_settle`), Python decoded-pixel `unchanged_from_previous`, lossless `player_source` `crop`, direct-route token-rate enforcement (separate from policy-neutral `PROVIDER_PROFILES` refactor), and `cites` fate.
- **Unknown.** Whether live `bm25_1hop` + compact `player-knowledge/3` hits raise on-demand query adoption above the pre-`#937` baseline, whether `recent_intents` improves post-cut task continuity in live play, and whether real provider caching behaves identically on bounded title-first recall indexes remain unverified until offline replay and live qualification run.
- **Decision needed.** Owner votes on the 15 single-topic items in the Decision Ballot (§9) once iterative three-family audits reach convergence. No `player-host/12` code or `S-MIGRATION` starts before approval.

## 1. Architectural invariants and `#177` compatibility

Every change in this RFC preserves:
- **`ADR 006` (`P-GENERALITY`):** Zero game semantics in `harness/computer/`, `harness/player/`, or `tools/player_host/`. Any settle/pixel-diff/crop mechanism operates strictly on mechanical pixels, dimensions and monotonic timestamps.
- **`ADR 008` (`lint-imports`):** Spectator/evaluator isolation stays intact; every serialized player HTTP attempt retains exact `context-manifest` digests ([owner decision](../decisions/owner-decisions.md#host-records-every-request-manifest); recall requests emit payload hashes as today).
- **`ADR 009`:** The curator remains the sole durable memory writer; the player gains no durable write tool. `recent_intents` in `BEGIN CONTEXT CUT` re-presents the same actor's own validated public emissions ephemerally.
- **Forward compatibility with `#177` (Programs & Monitor):** Actor ports (`computer_*`, `player_source`, `player_knowledge_*`) stay host-agnostic; full-resolution `computer-source/1` PNGs stay immutable; provider/spend plumbing stays role-neutral; no `#177` fields (`expectation`, `goal`, `confidence`, `flags`) are added early ([owner decision](../decisions/owner-decisions.md#tool-intent-required-and-cites-optional)). If opt-in `settle` (<= `2.0 s`) is adopted, holding `ComputerRuntime.serial` adds up to `2.0 s` of preemption latency within the existing `15 s` operation horizon.
- **Control discipline ([control rule](../standards/authority.md#control-review)):** Items lacking observed `#896` failure evidence — update-lead clipping (max `928` chars), a pre-dispatch turn-image guard (max `3` vs. `39`), `player_finish` defaults (`0` errors), and a new Node JSON-Schema dependency (`#925` reaffirmed zero Node dependency) — are deliberately excluded.

## 2. Bounded briefings and context-aware recall (`player-host/12`)

### 2.1 Bounded actor-start briefing
In `#896-b`, actor-start briefings grew from `178` chars (admission 1, `A01`) to `27,895` chars (admission 4 actor `002`, `A04/002`) and `51,601` chars (admission 10 actor `001`, `A10/001`), while `#920` capped only post-cut `cutBriefing` at `24,000` characters. Under `player-host/12`:
- Actor-start briefings budget the **final serialized JSON envelope** (including escaping, `coverage` and `unlisted_entries`) within `24,000` characters (`CUT_BRIEFING_CHARS`), inheriting `cutBriefing`'s total entry caps (`CUT_BRIEFING_ARTICLES = 64` total kept articles across tier 1 + tier 2; `CUT_BRIEFING_FACTS = 24` total kept standalone facts across tier 1 + tiers 3–4), `1,000`-character snippet clipping, and skip-if-oversized rule (`tools/player_host/knowledge.mjs:337-340`).
- **Deterministic tiered selection order:** (1) recall-selected `leads` (in recall selection order), then remaining entries as `index` rows in fixed tier order: (2) articles sorted by `last_confirmed.order` descending, (3) non-`instance_state` standalone facts sorted by `seen.order` descending, and (4) `instance_state` standalone facts sorted by `seen.order` descending. Define one explicit descending comparator (`b.order` vs. `a.order`, breaking equal-`order` ties by **ascending delivered order** `a.at - b.at`) and migrate `cutBriefing` (`tools/player_host/knowledge.mjs:310-312, 344, 347`, which currently reverses `byPosition(...)` and therefore breaks ties in reverse delivered order) to that same comparator so actor-start briefings, `cutBriefing`, and the recall index share one tie-break order. Kept entries appear in delivered order; `unlisted_entries` counts omitted entries; `player_knowledge_read` and `player_knowledge_query` reach every entry.
- **Live updates:** `updateDelivery` keeps its diff semantics (`added`/`updated`/`removed`, `knowledge.mjs:407-429`) with **no** clip on ordinary update leads (observed `#896-b` max lead `928` chars; max update payload `3,977` chars). Empty-to-populated first adoption budgets its serialized `index` payload under the same `24,000`-character tiered cap so an initial live adoption cannot exceed capacity.

### 2.2 Context-aware recall deduplication, bounded title-first index and delivery attribution
In `#896-b` (manifest order), `71.1%` (`278/391`) of pre-cut reminder leads and `100.0%` (`2,721/2,722`) of post-cut reminder leads repeated leads already sitting in the request; even on `main`, all `47` `v91` article leads fit inside `cutBriefing` (`11,117` chars `<= 24,000`).
- **Normalized active-lead tracking:** Compute each record's fingerprint over its **unclipped** delivered lead projection `fingerprint(item) = sha256(canonical({id, title: item.title ?? item.subject ?? item.id, lead: item.lead ?? item.text, status: statusOf(item)}))`. Reconstruct the active map chronologically from surviving placements, setting or updating a fingerprint **only** when a placement conveys the **complete (unclipped)** lead (an unclipped briefing `lead` with length `<= CUT_BRIEFING_SNIPPET_CHARS`, an update `added`/`updated` carrying a lead, or a reminder `lead`). Clipped briefing leads (`> 1,000` chars) and index-only rows stay outside `already_in_context` and remain eligible for full-lead recall; `removed` deletes that ID; surviving reminders never overwrite a newer version's fingerprint already in the fresh briefing. When `updateDelivery` (`knowledge.mjs:407-429`) emits an `updated` article `{id, title, lead, status?}` (including a body-only revision whose `lead` is unchanged), that placement carries the unclipped `lead` and therefore sets or updates the article's active lead fingerprint just like any other lead-bearing `updated` entry.
- **Cache-safe `already_in_context` hint:** Define `already_in_context` strictly in code as the sorted IDs whose active fingerprint equals the adopted version's unclipped lead fingerprint. Place `"already_in_context": [...]` inside recall **user message 2's JSON** immediately after `recent_calls` (before trailing screenshot image parts), leaving user message 1 (`{"index": [...]}`) **byte-identical across all recalls of one version** so prompt caching is preserved. Instruct the recall model to select only IDs outside `already_in_context` and return `{"articles": []}` when nothing new applies.
- **Bounded title-first recall index & deterministic overflow:** Budget the **final serialized JSON** of recall user message 1 within `24,000` characters (`max_index_chars`, frozen per version). Because message 1 is sent **before** recall produces a selection, order rows strictly by **§2.1 tiers 2–4** using the explicit descending comparator above (breaking equal-`order` ties by ascending delivered order `a.at - b.at` — never tier 1 recall-selected leads, which apply only to the subsequent briefing) so the index depends solely on the adopted version and remains byte-stable across recalls of that version:
  1. First build compact `{id, title, status?}` rows (clipping individual titles at `120` chars without splitting surrogate pairs) in §2.1 tiers 2–4 order. If compact title rows alone exceed `max_index_chars` (on `v91`'s `47` articles + `175` standalone facts, title-only rows already use `17,738` chars), keep rows in §2.1 tiers 2–4 order until the budget is full (skipping any single oversized row) and record `unlisted_entries` (omitted entries remain reachable via `player_knowledge_read`/`player_knowledge_query`).
  2. If budget remains after all compact rows fit, spend remaining budget adding first-sentence `index` snippets in §2.1 tiers 2–4 order (skipping entries that do not fit).
  3. Validate recall selections and compute the pre-fetch `all-delivered` skip strictly against the **exact index rows sent**; if no sent row lies outside `already_in_context`, emit `knowledge-recall` (`status: "not-made", reason: "all-delivered"`) and skip the HTTP fetch. At placement, re-filter against the adopted version and final projection; if no entry survives, skip injecting a reminder message (emitting no `knowledge-delivery` and recording `knowledge-undelivered` with `reason: "already-in-context"`, never emitting a second `knowledge-recall` event for the same `request_id`). Keep the original selected IDs in `knowledge-recall` for diagnostics, while `tools/memory_measure.py:678, 695-696, 716-718` credits delivered recall exposure and precision strictly from the successful `knowledge-delivery` placement's `fact_ids` (so leads stripped by placement-time re-filtering after an intervening update are never credited to that reminder).
- **Priced transient recall fallthrough (Ballot 3):** Only if approved, preserve transient HTTP/transport classification independently of pricing and allow fallback to the next normal `recall.every` cadence **only** when the failure is an independently classified transient HTTP/transport error with exactly one `response-complete` carrying usable provider-reported cost (including explicit `"0"`). Permanent errors, unpriced failures, or malformed cost keep `recallDisabled = true`.
- **Logical delivery outcomes (non-ballot telemetry alignment):** Retain per-attempt payload hashes and billing independently. Under `telemetry_version: 12`, every `knowledge-delivery` carries an explicit `outcome`:
  - `"delivered"` (on `briefing`, `reminder`, `update`): emitted **only** when the logical player request reaches a settled successful `response-complete` with usable cost; carries `receiving_player_request_id`, `text`, `article_ids`, `fact_ids`, `index_ids`, `delivered_knowledge_schema`, `version`, and `recall_request_id`.
  - `"undelivered"` (on `briefing`, `reminder`, `update`): emitted on **every** other terminal outcome for a logical request carrying that placement that did not meet the `"delivered"` condition (including all attempts failing pre-headers, terminal HTTP 4xx/5xx such as two 503s, aborted/incomplete stream, `cost-unreported`, and priced terminal failure such as `stopReason: "length"` with a valid provider charge — keeping attempt billing and pre-request `update` `"refused"` independent); carries the same placement fields (`receiving_player_request_id`, `text`, `article_ids`, `fact_ids`, `index_ids`, `delivered_knowledge_schema`, `version`, `recall_request_id`, plus `previous_version`, `coverage`, and `removed_ids` on `kind: "update"` per `knowledge.mjs:427-429` and `player-host-telemetry.md:16-22`) attached to the failed logical request.
  - `"refused"` (on `update` only): pre-request update refusal (including `reason: "context-capacity"`), preserving `docs/contracts/player-host-telemetry.md:23-29` with no `receiving_player_request_id`, `text`, or `fact_ids`.
  - **Consumer accounting:** Capture each actor's `host_telemetry` (`telemetry_version`) from its opening `host-start` event (`harness/evaluation/core/sources.py:437-446`). Update the **three delivered-exposure consumers** (`tools/memory_measure.py:675-683`, `harness/evaluation/core/host.py:329`, `harness/viewer/telemetry.py:238-244` — applying the delivered predicate while keeping `kind == "briefing"` for `out.briefings`, `kind in ("briefing", "update")` for `out.latest_version` so stale reminders never regress version, and reading `receiving_player_request_id` with `request_id` fallback) to count delivered exposure when `fields.get("outcome") == "delivered"` (on **every** admitted version, preserving all `/9` and `/11` delivered updates as well as `/12`) **or** `(host_telemetry in (5, 8, 9, 11) and kind in ("briefing", "reminder") and "outcome" not in fields)` (preserving admitted archived `/5`, `/8`, `/9`, and `/11` `briefing`/`reminder` rows without `outcome` while rejecting malformed `/12` rows). Update both spectator views: in Watch (`web/app/watch.js:181, 263, 318`, receiving `outcome` from `harness/viewer/feed.py:181`), render `"undelivered"` updates explicitly (not `"Memory updated"`) and require `outcome === "delivered"` for the successful-update filter and link; in Recorded Knowledge (`web/app/records.js:379-384`, reading `harness/viewer/knowledge.py:274`), give `"undelivered"` placement rows outcome-aware labels (`"Attempted lead:"` / `"Attempted index:"`) while preserving their diagnostic text and keeping `"Delivered lead:"` / `"Delivered index:"` for delivered and admitted historical deliveries. By contrast, `tools/host_analysis.py:474` (`composition_pairs` prompt-injection exclusion, `:144-166`) does **not** measure player exposure and therefore **keeps** `event.get("outcome") != "refused"` so priced `stopReason: "length"` `"undelivered"` `reminder`/`update` prompts remain excluded from OLS `usage_fit` via `receiving_player_request_id` (un-fetched failures without `prompt_tokens` are already excluded by `usage_unknown` at `:150`).

## 3. Formal `context_cut` hysteresis, halving notices and continuity

### 3.1 Hysteresis, strict-fit hard-capacity rescue and atomic update+cut
Let `T` be estimated tokens of the **post-image-projection** candidate request minus `currentBriefingTokens`, `I` raw active images, `P` protected latest-batch images, `M = max_context_images`, `B = context_image_block`, `H = high_mark`, `L = low_mark`, and `O_-` the prior projection's omitted image count. Define one strict hard-fit predicate:
$$\text{fits}(R) \iff \text{estimatedTokens}(R) + \text{model.maxTokens} < \text{model.contextWindow}$$
and for `P <= M`:
$$O(I, P) = \min\!\left(I - P,\; B \left\lceil \frac{\max(0, I - M)}{B} \right\rceil\right)$$
All cut searches below require the three contract guards: cuts enabled (`context_cut !== null`), `!cutRestored`, and no accepted `orderly_stop`.

1. **Arm on pressure (edge-reported holds):** Under the three guards, arm `cutDemand = true` when `T > H` or `O(I, P) > O_-`. If eligible covered whole turns `E < min_free`, keep `cutDemand = true`, emit **one** `held-back` event on entering that `(reason, coverage_frontier)` state, and run standard image-block eviction. Re-evaluate only when the eligible covered frontier advances, a protected turn becomes eligible, or a newly adopted version changes the plan. Clear `cutDemand` on an applied cut, permanent restore, or accepted `orderly_stop`; reset `O_-` to the post-cut projection's omitted count.
2. **Smallest sufficient covered prefix & `insufficient-cover` hold:** When `cutDemand` is armed and `E >= min_free`, evaluate every `k` from `min_free` through `E` (never breaking before `min_free`). For each `k`, build the exact candidate suffix + fresh `cutBriefing` + serialized `cutMarker` + retained notices `R_k` and compute `(T_k, I_k)` with the same briefing subtraction. Select the **smallest** `k in [min_free, E]` satisfying `T_k <= L`, `I_k <= M - B`, **and `fits(R_k)`**. If **no** `k in [min_free, E]` meets all three conditions (and the uncut candidate request `R` still satisfies `fits(R)`), do not apply an exhausted partial cut: keep `cutDemand` armed, emit one `held-back` edge event with `reason: "insufficient-cover"`, and apply standard block eviction.
3. **Independent strict-fit hard-capacity rescue:** Under the same three guards, independently of `T > H` and `min_free`, whenever the uncommitted candidate request `R` (with active notice, `maxTokens`, and briefing — either because no normal cut was selected above or because `cutDemand` was false / `E < min_free`) fails `fits(R)` (i.e., `>= contextWindow`) and `E >= 1`, search the **original uncommitted projection** over `k in [1, E]` for the smallest covered prefix `R_k` satisfying `fits(R_k)` and strictly reducing total tokens (`estimatedTokens(R_k) < estimatedTokens(R)`); if none satisfies, retain the existing `context-capacity` stop. Commit at most one prefix rewrite per transform.
4. **Atomic joint update+cut planning (distinct from `#946`):** Whereas `#946` fixes only the narrow `player-host/11` defect where `pendingKnowledgeUpdates` was discarded against pre-cut capacity when a same-turn cut freed room, `#947` introduces full side-effect-free joint planning: starting from the newest admissible staged version down to the currently adopted version, build the joint plan (using coverage at or below that candidate version, its `cutBriefing` if cutting, surviving corrections/removals omitted by the cap, `cutMarker`, and active notice). Admit a newer version only when its final projected candidate request `R` satisfies **both** `fits(R)` **and** the existing update capacity-warning threshold (`estimatedTokens(R) + context_reserve_tokens < model.contextWindow`, `docs/contracts/player-host.md:339-340`, `host.mjs:1401`), and commit version, frontier, cut, placements, fingerprints and telemetry atomically for the newest admissible candidate. If a newer version fails that threshold, emit `knowledge-delivery` with `kind: "update", outcome: "refused", reason: "context-capacity"` (matching §2.2 and `player-host-telemetry.md:23-29`, without `receiving_player_request_id`, `text`, or `fact_ids`) and retain/cut on the prior version.

### 3.2 Halving-step tail notices (Ballot 5)
Preserve exact telemetry wire names (`context-capacity`, `host-timeout`, `spend-limit` in `tools/host_analysis.py:482`) and emit `tail-notice` only on actual placement with its receiving `request_id`. Instead of appending a new notice on every turn, emit each kind when remaining room crosses fixed halving steps (`100%`, `50%`, `25%`, `12.5%` of its warning threshold), wording remaining amounts/time as measured at that request, combining simultaneous crossings into one append-only user message, and emitting **no further notice below `12.5%`** (spend exhaustion is delivered via `spend-reserve-reached` / `orderly_stop`; context and time end with the existing host stop). On a cut, reset the `context-capacity` step tracker and re-evaluate against the post-cut projection.

### 3.3 Ephemeral `recent_intents` in `BEGIN CONTEXT CUT` (Ballot 6)
Include `"recent_intents"` in the `BEGIN CONTEXT CUT` single-line JSON block: the last `5` distinct validated public `intent` strings from **committed, non-refused actor tool calls** in this actor's removed turns (excluding `player_finish` and refused/malformed calls; accumulated across cuts when a cut removes fewer than `5` new turns; deduplication keeps the **most recent** occurrence at the tail in chronological order), clipped to `160` characters without splitting surrogate pairs, with the full serialized marker cost included in every cut candidate.

## 4. Terminating spend-limit and `finish_reserve` handshake (Ballot 7)

To close the race where ordinary work exhausts `spend_limit_usd` before the driver's `100 ms` poll issues `orderly_stop`:
1. **Preflight admission (`tools/campaign_package.py`):** Require `ending_reserve.usd + reserve_bound < spend_limit_usd` (preventing Turn-1 immediate deadlock while keeping existing `ending_reserve.usd >= reserve_bound`).
2. **Ordinary-work admission (`tools/player_host/host.mjs`):** When no `orderly_stop` control is projected into the request, admit a player fetch (or transport retry) only while:
   $$\text{spent} + \text{in\_flight\_recall\_bound} + \text{finish\_reserve} + \text{unpriced\_bound} < \text{spend\_limit}$$
   Equality fails admission. If the *only* obstruction is an in-flight recall reservation, await recall settlement and recheck once.
3. **One-shot `spend-reserve-reached` handshake:** When ordinary admission still fails (and `spent < spend_limit`), emit one actor-bound `spend-reserve-reached` telemetry event (`actor_id`, `spent_usd`, `spend_limit_usd`, `finish_reserve_usd`, `unpriced_bound_usd`) and wait up to `2 s` for `orderly_stop` on stdin. The live driver (`tools/campaign_player.py`) consumes `spend-reserve-reached` on its poll loop (alongside its existing `dollars <= ending_reserve.usd` check) and immediately issues or reuses its `orderly_stop` request unless Pause, channel stop, or hard limit already fired.
4. **Explicit non-masking terminal settlement:** During the `2 s` wait, preserve any independent triggering stop reason without masking it: Pause/operator cancellation keeps its cancellation reason, host/custodian deadline keeps its deadline reason, `spent >= spend_limit` keeps `"spend-limit"`, and stdin EOF settles with the existing control-EOF failure reason. Emit `"spend-reserve-timeout"` **only** when the `2 s` wait expires cleanly with no `orderly_stop` (e.g., standalone host conformance run without a driver).
5. **Control-gated reserve release:** Release `finish_reserve` **only** for a request whose projected context actually contains the accepted `control_id`. If `orderly_stop` arrives while an ordinary request or retry is unsent or in backoff, supersede that unsent ordinary body and build a fresh finish-up request carrying the control message; attempts already sent retain their retry identity and settlement.

## 5. `player-knowledge/3` compact query, Porter2 stemmer & parity vectors

### 5.1 Discriminated compact query hits (Ballot 8) and casefolded title lookup (Ballot 9)
- **Discriminated envelope (`player-knowledge/3`, Ballot 8):** `player_knowledge_read` keeps `"records": [full_record]` (`resolution` unchanged). `player_knowledge_query` returns `"resolution": "query", "hits": [...]` (up to `10` hits, ordered by `bm25_1hop` score) with closed per-kind shapes:
  - **Article hit:** `{id, kind: "article", revision, title, snippet (lead clipped <= 240 chars), tags, via: "match" | "hop"}` plus optional non-empty `status`.
  - **Fact hit:** `{id, kind: "fact", subject (string | null), claim_kind, scope, snippet (text clipped <= 240 chars), cited_by_articles (up to 3), via: "match" | "hop"}` plus optional non-empty `status`.
  - Across the `20` `#924` `v91` queries replayed in `#936` (comparing exact `Knowledge._result` envelopes serialized via `harness.jsonio.canonical` [`harness/jsonio.py:31`] UTF-8 bytes under the schema-valid `/2`→`/3` projection documented in [player architecture research](../research-player-architecture.md), where the raw `/2` full side is a conservative lower bound for `/3`), compact hits reduce total bytes by **`64.0%`** (`232,144 B` → `83,508 B`) and median payload by **`62.0%`** (`10,946 B` → `4,155 B`, max `15,193 B` → `4,457 B`).
- **Consumer & measurement migration (preserving `judge.ROUTES`):** Update `harness/player_view.py` to validate discriminated `player-knowledge/3` read/query forms, and `harness/evaluation/core/host.py` + `harness/viewer/knowledge.py` to project `hits` IDs alongside `records`.
