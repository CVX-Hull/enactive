# One bounded fresh-character seven-day attempt

For [#81](https://github.com/CVX-Hull/enactive/issues/81) and
[#82](https://github.com/CVX-Hull/enactive/issues/82), turn the accepted
[first-day rehearsal](../acceptance/2026-10-18-first-day-completion.md) and
[two-phase operator result](../acceptance/2026-10-18-campaign-operator.md) into an
executable deciding campaign. **This proposal is not admission or survival success.**
Independent readiness, completed tracker split, candidate checks and fresh native
preflight must precede a separate frozen local admission. The goal remains the
same normally created character alive after seven elapsed game days, with needs,
shelter/rest and meaningful supply/travel/threat decisions and a watchable UI.

The lead prepares one fresh character and verifies each daily checkpoint; player A
handles days 1–3, and a new player B takes over at the day 4 restart. Each daily
assignment has at most 300 charged inputs and two wall hours. The whole attempt,
including creation, recovery, review and publication, has 2600 inputs and 24 wall
hours. These are ceilings, not permission to keep playing after a stop condition.

## Reuse, capability and risk

Use the existing native-v3 controller/CLI, prepared windowed bundle/project userdir,
Pause, original journals, shared argparse grammar, bounded one-off capture and
source-linked checkpoints. Lead alone owns source, lifecycle, admission, escalation
and final verification. One designated general-purpose player owns ordinary input;
no simultaneous waypoint lease, source writer or second game. Read-only independent
reviews can run in parallel. No new dependency, agent framework, paid API, global
configuration, memory database, custom source history or model tier is selected.
The lead owns the one-off capture's maintenance; revisit reuse/retirement under
#75 if repeat use, defects or cost justify a maintained tool. Git owns source.

## Game-time and native activity bounds

A day means the fixed intervals from T0, not wall midnight or a reset after handoff.
Milestones are T0+24k game hours for k=1..7. Stop at the first supported normal
boundary after each milestone; actual overshoot may be at most1game hour. Final
success requires **168..169elapsed game hours**, same character and maintained
needs; crossing169hours fails this acceptance rather than extending authority.
Plan requested activity duration within the remaining next-milestone interval;
retain actual overshoot, never manufacture elapsed time.

Before/after activities inspect current health, needs, temperature, weariness,
shelter, supplies and threats. Native Pause does not cancel committed activity.
Use only ordinary visible choices with a bounded requested interval:

- Wait at most30game minutes per request, at most12requests/6requested hours per
  fixed day, only for a legitimate needs/recovery/scheduling choice with adequate
  observed shelter/supplies. No idle starvation or calendar-only strategy.
- Sleep with a visible alarm at most4hours per request, at most3requests/12requested
  hours per fixed day, based on actual tiredness and prepared needs/shelter. The
  historical UI showed3/4hour choices; a shorter alarm is not yet a proven outcome.
  Do not select indefinite sleep or claim continuous sleep from calendar difference.
- Other long work/cooking/reading/crafting needs a visible bounded estimate at most
  2hours per request and a batch fitting needs/time/milestone. No indefinite repeats.

## Handoff, retention and stop rules

A new or returning actor receives a bounded source-linked checkpoint, current phase,
original remaining limits and fresh Observe; explicit Resume grants only fresh
ordinary authority. Lead inspection waits for Pause, terminal tool handles,
explicit quiescence and no live request/recovery/lease, then fresh paused Observe.
No old relative coordinates or execution capability survives restart. The day4
context replacement is actual new-player input, not advisory reading alone.

Unexpected user Pause/native human takeover revokes the active phase. The player
stops and hands off; no automatic Resume. Intentional user takeover requires user
resumption/authorization. This is distinct from declared lead inspection and fresh
actor reassignment. Actor strings and inherited tool permissions are not isolation.

under `.runtime/campaigns/seven-day-campaign-001/`. Maximum**1GiB**, stop investigation
