character spawned. The next work combines [#79 continuity](https://github.com/CVX-Hull/enactive/issues/79)
and [#80 first day](https://github.com/CVX-Hull/enactive/issues/80): prove a usable
survival loop and a handoff that retains its facts, uncertainty and resources.
This is a prospective development brief, not accepted capability or permission
to repeat the stopped pilot. GitHub owns readiness and subsequent scope changes.

in history. Do not resume pilot001 or replenish any of its budgets.

## Minimum advisory handoff

Start with a short Markdown/JSON artifact and the existing source/journal/frame
references. It is a player-readable handoff, not a new executable persisted contract
or second work tracker. Before choosing an action, a replacement must inspect:

| Information | Review and authority rule |
| --- | --- |
| Objective and next decision | Public purpose, completed/remaining work and concise reason; no stored executable input or private reasoning transcript |
| Character/world/scenario | Actual creation/load menu and character-name evidence, visible calendar and current session; never infer identity from relative coordinates alone |
| Facts and uncertainty | Label current direct observations, last-seen facts, hypotheses, absent observations and disputed/unresolved outcomes with original source IDs |
| Resources | Original limits, every charged input including unknown/rejected requests and cleanup, elapsed wall time including pauses/reasoning/recovery, game-time reference and any native activity overshoot |
| Applicability | Exact source/native configuration and episode, fresh Observe and explicit authorization; discard old coordinate applicability and restore no lease/task |
| Stop/review state | Live pending request separately from historical unknowns; last stop, eligibility for cleanup and explicit next segment admission decision |

Use existing journals and immutable capture references; keep one small current
advisory summary plus retained checkpoint versions. Initially bound each summary
to 8 KiB, at most 32 source references and 24 checkpoints for one rehearsal. Bound all
retained captures to 256 MiB. Stop before capacity exhaustion; no silent eviction or
save deletion. Git owns source history; these bounds are evidence retention, not
a replacement for version control. Retire advisory applicability at campaign end,
preserving the evidence under the runbook. Reassess limits from actual use.

Missing/corrupt accounting, duplicated/omitted charges, decreasing totals, wrong
identity or inaccessible required evidence must stop before new input. Demonstrate
those negative checks with copied advisory fixtures and the genuine source journal,
separate from native success. Existing portable checks validate source changes;
manual review remains responsible for aggregate campaign accounting and semantic
identity. If a small enforcement adapter becomes necessary, first freeze its scope,
caller/migration contract and disjoint ownership; this brief does not claim it exists.

First exercise the spectator's existing recorded objective, timeline and evidence
details with goal/progress, consumed/remaining budgets and stop reason. Let a fresh
reviewer inspect the explanation at ordinary size. Add UI only for a demonstrated
missing view, with named paths and acceptance before writing it. The waypoint card
continues to describe waypoint tasks; it must not imply an unimplemented survival
supervisor is running.

## Lifecycle boundaries and unknown effects

Current native wire v3 deliberately clears pending acknowledgment when a world
enters/exits and replaces its session. A longer timeout does **not** change that.
Do not count entry/save/quit delivery as completed gameplay, relax the controller,
fake an acknowledgment or turn a later scene into an old action receipt.

Before the rehearsal is Ready, independently review and freeze its episode-boundary
procedure for intended creation entry, normal save/quit and reload. Each boundary
stops the previous episode, retains its exact receipt/unknown and charged totals,
and has no outstanding skill/waypoint task. Observe only after native expiry when
needed. Distinguish three admissions: ordinary creation menus; bounded identity
inspection when the name is not yet visible; and survival decisions only after
the actual character/world and current state are established. All preserve the
original cumulative limits. No old task continuation or replay.

After a declared creation/load transition, an inspection-only episode may use a
fresh supported normal-play frame after reconciliation, no live pending/control
request or lease, and explicit Resume. It permits at most **four charged inputs
and two minutes**, within the same total envelope, solely to open the actual
player-info view (`@` in the source default bindings), inspect its rendered name,
and leave through its displayed Quit/ESC control. Do not modify the character,
move, use supplies or rest. Reject unreadable, conflicting or unavailable identity,
an unsupported/rejected input or any new unknown; do not guess a menu sequence.
Pause after inspection. Current `PLAYER_INFO` is an explicitly supported menu;
the initial structured scene contains no character name and cannot supply it.

Match current player-info evidence with the actual selected world/save and
creation-name evidence, with no other selection or process intervening. Use visible
calendar/needs/inventory for restart comparisons; relative coordinates never prove
identity. A same-name/world ambiguity stops. The lead records the matching evidence
and its semantic limits, then obtains fresh Observe and explicitly reauthorizes
survival input. Name inspection grants no survival progress or retrospective receipt,
and is not cryptographic engine identity. Normal save/load must be demonstrated,
not inferred from this source procedure.
Unresolvable identity, unexpected unknowns, a still-live pending effect or missing
accounting stops the rehearsal. Historical unknowns remain unknown and cannot earn
task progress; current calendar/needs can support new observations on their own.
If this cannot be implemented with existing controls, retain the failure and scope
a bounded real blocker before another attempt. This is a readiness gate, not a
silent exception added during play.

## Survival families, review and allocation

The capable player selects direct inputs from current evidence: inspect needs and
inventory; find actually usable food/clean water; inspect/use a supply; assess
weather/clothing/shelter; conduct a visible supply excursion and return; manage
ordinary rest/activity. Supply descriptions and consumption messages must support
the semantic outcome. Threats cause a fresh bounded retreat/plan decision or stop;
do not manufacture a threat if none is encountered. Crafting/purification is added
only if the actual scenario requires it, before expanding a generic skill schema.

Checkpoint at spawn/initial resources, supply and shelter decision, player handoff,
normal save/restart and first-day endpoint, plus every material failure. Use the
existing campaign finding/disposition workflow, including unexercised/no-change
areas, and separate portable/native/semantic evidence. A first-day success cannot
establish general monitor efficacy, causal improvement or seven-day readiness.

verification. Parallel read-only reviewers may inspect immutable evidence or
